# Git workflow

# Правила работы с Git

## 1. Структура веток

В проекте используются следующие основные уровни веток:

```text
master
└── dev
    ├── mamooin
    │   ├── feature/auth
    │   ├── fix/token-validation
    │   └── refactor/user-service
    │
    ├── frontend-developer
    │   ├── feature/profile-page
    │   └── fix/mobile-layout
    │
    ├── backend-developer-1
    └── backend-developer-2
```

### `master`

`master` — стабильная ветка проекта.

В ней должен находиться код, который:

- прошёл проверку;
- успешно собирается;
- проходит тесты;
- готов к демонстрации, тестированию или развёртыванию.

Прямые коммиты и прямой `push` в `master` запрещены.

Изменения попадают в `master` только через Pull Request из ветки `dev`.

```text
dev -> master
```

Перед объединением `dev` с `master` необходимо убедиться, что:

- проект собирается;
- тесты проходят;
- миграции базы данных применяются;
- нет известных критических ошибок;
- изменения проверены командой.

---

### `dev`

`dev` — основная ветка активной разработки.

В ней объединяется работа всех участников команды.

Прямой `push` в `dev` запрещён. Изменения должны попадать в неё только через Pull Request из персональных веток разработчиков.

```text
mamooin -> dev
frontend-developer -> dev
backend-developer-1 -> dev
backend-developer-2 -> dev
```

Каждый Pull Request в `dev` должен быть проверен хотя бы одним другим участником команды.

Автор Pull Request не должен самостоятельно подтверждать и объединять собственный Pull Request без проверки, кроме экстренных случаев.

---

### Персональные ветки разработчиков

У каждого разработчика есть собственная постоянная ветка, созданная от `dev`.

Пример:

```text
dev
├── mamooin
├── frontend-developer
├── backend-developer-1
└── backend-developer-2
```

Персональная ветка используется как рабочая область конкретного разработчика.

Разработчик может:

- создавать от неё дополнительные ветки;
- объединять в неё собственные изменения;
- самостоятельно определять внутреннюю структуру веток;
- исправлять историю своих внутренних веток до создания общего Pull Request.

Другие участники команды не обязаны проверять внутренние Pull Request между ветками одного разработчика.

Главный Pull Request разработчика создаётся из персональной ветки в `dev`.

Пример:

```text
feature/auth -> mamooin
mamooin -> dev
```

Именно Pull Request вида `персональная-ветка -> dev` предназначен для командного Code Review.

## 2. Создание персональной ветки

Первоначально персональная ветка создаётся от актуальной ветки `dev`.

```bash
git switch dev
git pull origin dev
git switch -c mamooin
git push -u origin mamooin
```

Название персональной ветки должно быть коротким и однозначным.

Можно использовать:

- имя;
- никнейм;
- корпоративный логин;
- фамилию латиницей.

Примеры:

```text
mamuin
ivan
petrov
alex-backend
```

Не рекомендуется использовать названия:

```text
my-branch
test
new
work
branch1
```

## 3. Внутренние ветки разработчика

От персональной ветки рекомендуется создавать отдельную ветку под каждую самостоятельную задачу.

Пример:

```bash
git switch mamuin
git pull origin mamuin
git switch -c feature/authentication
```

После завершения работы ветка может быть объединена с персональной веткой:

```bash
git switch mamuin
git merge feature/authentication
git push origin mamuin
```

После успешного объединения локальную ветку можно удалить:

```bash
git branch -d feature/authentication
```

Удаление ветки на сервере:

```bash
git push origin --delete feature/authentication
```

### Рекомендуемое именование внутренних веток

Формат:

```text
<тип>/<краткое-описание>
```

Типы веток:


| Тип     | Назначение                                                                        |
| ---------- | ------------------------------------------------------------------------------------------- |
| `feature`  | Новая функциональность                                                 |
| `fix`      | Исправление ошибки                                                         |
| `refactor` | Изменение структуры кода без изменения поведения |
| `test`     | Добавление или изменение тестов                                 |
| `docs`     | Документация                                                                    |
| `chore`    | Технические изменения                                                   |
| `build`    | Сборка и зависимости                                                      |
| `ci`       | CI/CD и GitHub Actions                                                                     |
| `db`       | Миграции и изменения базы данных                                |

Примеры:

```text
feature/user-registration
feature/product-search
fix/invalid-access-token
fix/order-creation
refactor/user-service
test/auth-handler
docs/api-description
db/add-orders-table
ci/add-github-actions
```

Названия веток должны:

- писаться латиницей;
- использовать строчные буквы;
- разделять слова дефисами;
- кратко описывать задачу.

Плохие примеры:

```text
feature
new-feature
fix123
MY_BRANCH
final-version
test2
```

## 4. Актуализация персональной ветки

Перед началом новой задачи разработчик должен получить последние изменения из `dev`.

Рекомендуемый вариант:

```bash
git switch dev
git pull origin dev

git switch mamuin
git merge dev
```

После разрешения возможных конфликтов:

```bash
git push origin mamuin
```

Перед созданием Pull Request в `dev` персональная ветка также должна быть синхронизирована с актуальным состоянием `dev`.

```bash
git switch dev
git pull origin dev

git switch mamuin
git merge dev
```

Конфликты должен разрешать автор изменений.

Не следует перекладывать разрешение конфликтов на человека, который проводит Code Review.

## 5. Правила коммитов

Коммит должен описывать одно логическое изменение.

Хороший коммит:

- добавляет одну законченную возможность;
- исправляет одну конкретную ошибку;
- изменяет один связанный участок системы;
- может быть отдельно понят и проверен.

Не следует объединять в одном коммите:

- новую функциональность;
- исправление случайной ошибки;
- форматирование всего проекта;
- изменение зависимостей;
- переименование файлов, не связанное с задачей.

## 6. Именование коммитов

Для сообщений коммитов используется формат Conventional Commits:

```text
<тип>(<область>): <краткое описание>
```

Область указывается при необходимости.

Примеры:

```text
feat(auth): add user registration
fix(api): handle invalid access token
refactor(user): split user service
test(auth): add login handler tests
docs(api): describe authentication endpoints
db(order): add orders table migration
ci: add backend tests to GitHub Actions
chore: update dependencies
```

### Основные типы коммитов


| Тип     | Назначение                                                |
| ---------- | ------------------------------------------------------------------- |
| `feat`     | Новая функциональность                         |
| `fix`      | Исправление ошибки                                 |
| `refactor` | Рефакторинг                                              |
| `test`     | Тесты                                                          |
| `docs`     | Документация                                            |
| `style`    | Форматирование без изменения логики |
| `chore`    | Техническое обслуживание                     |
| `build`    | Сборка и зависимости                              |
| `ci`       | CI/CD                                                               |
| `perf`     | Улучшение производительности             |
| `revert`   | Отмена предыдущего изменения              |

### Требования к сообщению коммита

Сообщение должно:

- писаться на английском языке;
- начинаться со строчной буквы после двоеточия;
- быть коротким и конкретным;
- описывать результат изменения;
- не содержать точку в конце заголовка.

Хорошие примеры:

```text
feat(user): add profile update endpoint
fix(order): prevent creation with empty items
test(repository): add PostgreSQL integration tests
docs: add local development instructions
```

Плохие примеры:

```text
fix
changes
update
final
work
added some files
исправил баг
```

При необходимости коммит может содержать подробное описание:

```text
fix(auth): refresh expired access token

Add token expiration validation and generate a new access token
when a valid refresh token is provided.
```

## 7. Частота коммитов

Коммиты необходимо создавать регулярно, но каждый коммит должен сохранять логическую целостность.

Не следует:

- делать один огромный коммит за несколько дней работы;
- создавать коммит после изменения каждой строки;
- отправлять код, который не компилируется;
- оставлять временные отладочные изменения.

Перед коммитом необходимо проверить:

```bash
git status
git diff
```

После этого добавить только нужные файлы:

```bash
git add path/to/file
```

Не рекомендуется без проверки использовать:

```bash
git add .
```

Перед созданием коммита необходимо убедиться, что в него не попали:

- `.env`;
- пароли;
- токены;
- приватные ключи;
- локальные конфигурации IDE;
- временные файлы;
- собранные бинарные файлы;
- персональные настройки.

## 8. Pull Request из персональной ветки в `dev`

Pull Request должен содержать законченное и проверяемое изменение.

Не следует создавать один Pull Request сразу с большим количеством несвязанных задач.

Перед созданием Pull Request необходимо:

1. Обновить локальную ветку `dev`.
2. Объединить актуальный `dev` со своей персональной веткой.
3. Разрешить конфликты.
4. Собрать проект.
5. Запустить тесты.
6. Проверить список изменённых файлов.
7. Удалить отладочный код.
8. Проверить отсутствие секретов и лишних файлов.

## 9. Название Pull Request

Рекомендуемый формат:

```text
<тип>: <краткое описание>
```

Примеры:

```text
feat: add user authentication
fix: prevent duplicate order creation
refactor: restructure product service
docs: add database setup guide
db: add product and category migrations
```

Плохие названия:

```text
Update
Changes
My work
New PR
Final version
Fixes
```

## 10. Описание Pull Request

Каждый Pull Request в `dev` должен содержать описание.

Рекомендуемый шаблон:

```markdown
## Что сделано

- Добавлена регистрация пользователя.
- Добавлена проверка уникальности email.
- Добавлено хеширование пароля.

## Зачем

Необходимо для реализации авторизации пользователей в приложении.

## Как проверить

1. Запустить приложение.
2. Отправить POST-запрос на `/api/v1/auth/register`.
3. Проверить создание пользователя в базе данных.
4. Повторить запрос с тем же email.
5. Убедиться, что API возвращает ошибку.

## Изменения базы данных

- Добавлена таблица `users`.
- Добавлен уникальный индекс на поле `email`.

## Дополнительная информация

- Добавлены unit-тесты.
- Обновлена документация API.
```

Если какой-либо раздел не нужен, его можно удалить.

## 11. Code Review

Проверяющий должен обращать внимание на:

- корректность логики;
- соответствие архитектуре проекта;
- читаемость кода;
- обработку ошибок;
- наличие тестов;
- безопасность;
- работу с базой данных;
- обратную совместимость;
- отсутствие лишнего кода;
- соответствие задаче.

Комментарии должны быть конкретными и нейтральными.

Хороший комментарий:

```text
Здесь ошибка игнорируется. Лучше вернуть её вызывающему коду или
добавить обработку, иначе запрос может завершиться с некорректным результатом.
```

Плохой комментарий:

```text
Что это вообще такое?
```

Автор Pull Request должен:

- отвечать на комментарии;
- исправлять замечания;
- отмечать решённые обсуждения;
- не закрывать замечания без исправления или объяснения.

## 12. Объединение Pull Request

Pull Request в `dev` можно объединять, если:

- получено хотя бы одно одобрение;
- все обязательные проверки прошли;
- конфликты отсутствуют;
- замечания Code Review исправлены;
- проект собирается;
- тесты проходят.

Для Pull Request в `dev` рекомендуется использовать **Squash and merge**.

Это позволяет объединить внутренние рабочие коммиты разработчика в один понятный коммит.

Например, внутренние коммиты:

```text
feat(auth): add handler
fix(auth): fix handler
fix(auth): fix tests
style(auth): format code
```

после Squash могут стать одним коммитом:

```text
feat(auth): add user authentication
```

Для объединения `dev` в `master` можно использовать обычный merge-коммит, чтобы сохранить историю выпусков.

## 13. Экстренные исправления

Если критическая ошибка обнаружена в `master`, создаётся ветка от `master`:

```text
hotfix/<описание>
```

Пример:

```text
hotfix/authorization-crash
```

Порядок действий:

```text
master
└── hotfix/authorization-crash
```

После исправления создаётся Pull Request:

```text
hotfix/authorization-crash -> master
```

После объединения исправление необходимо также перенести в `dev`, чтобы ошибка не появилась повторно при следующем релизе.

```text
master -> dev
```

## 14. Запрещённые действия

Без согласования с командой запрещается:

- выполнять прямой `push` в `master`;
- выполнять прямой `push` в `dev`;
- использовать `git push --force` для общих веток;
- переписывать историю `master` или `dev`;
- удалять чужие ветки;
- объединять Pull Request с непройденными проверками;
- коммитить секреты и `.env`;
- добавлять сгенерированные или временные файлы без необходимости;
- объединять собственный Pull Request без Code Review;
- выполнять массовое форматирование кода вместе с функциональными изменениями.

`force push` допускается только в собственной внутренней ветке, если разработчик понимает последствия и никто другой не использует эту ветку.

Предпочтительно использовать:

```bash
git push --force-with-lease
```

вместо:

```bash
git push --force
```

## 15. Краткий рабочий процесс

Начало новой задачи:

```bash
git switch dev
git pull origin dev

git switch mamuin
git merge dev

git switch -c feature/task-name
```

Выполнение работы:

```bash
git add path/to/file
git commit -m "feat(module): add task functionality"
git push -u origin feature/task-name
```

Объединение внутренней ветки с персональной:

```bash
git switch mamuin
git merge feature/task-name
git push origin mamuin
```

Синхронизация перед Pull Request:

```bash
git switch dev
git pull origin dev

git switch mamuin
git merge dev
git push origin mamuin
```

После этого создаётся Pull Request:

```text
mamuin -> dev
```

После проверки и объединения изменений разработчик снова синхронизирует персональную ветку:

```bash
git switch dev
git pull origin dev

git switch mamuin
git merge dev
git push origin mamuin
```

## 16. Главное правило

Git-история должна позволять любому участнику команды понять:

- кто внёс изменение;
- какую задачу решает изменение;
- почему оно было сделано;
- как его проверить;
- в каком Pull Request оно обсуждалось.

Основная цель этих правил — не усложнить разработку, а сделать совместную работу предсказуемой, понятной и безопасной.

## Рекомендуемая модель

Для короткого хакатона подходят две постоянные ветки:

- `main` — только проверенные демонстрационные версии; всегда должна собираться и запускаться;
- `dev` — интеграционная ветка текущего спринта.

Персональные рабочие ветки создаются от актуальной `dev`, например `mamooin`, и возвращаются в неё через pull request. Имя `dev/<name>` использовать нельзя, пока существует ветка `dev`: Git не может одновременно хранить ссылки `dev` и `dev/<name>`.

## Поток изменений

1. Обновить `dev` и создать либо переключиться на персональную рабочую ветку.
2. Делать небольшие логические коммиты в Conventional Commits: `feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`.
3. Открыть PR из персональной ветки в `dev`; перед merge должны пройти lint, unit-тесты и сборка.
4. Перед контрольной точкой открыть release PR `dev -> main`.
5. После проверки поставить тег, например `v0.1.0-mvp` или `demo-2026-08-09`.

## Правила PR

- Минимум один участник проверяет изменения, если размер команды позволяет.
- В PR указаны цель, способ проверки, снимки UI для визуальных изменений и затронутые API-контракты.
- Merge предпочтительно через squash, чтобы история оставалась компактной.
- Прямые push в `main` запрещены; в `dev` — только для аварийной ситуации по решению команды.
- Изменение `RecapCard` или публичного API требует согласования frontend и backend.

## Почему эта схема

Одна `main` без интеграционной ветки рискованна при параллельной работе frontend/backend. Полный классический Git Flow для хакатона избыточен. `main + dev + персональные ветки` даёт понятную точку интеграции и сохраняет стабильную демонстрационную ветку.
